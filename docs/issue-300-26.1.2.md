# Death worm riding fix (#300)

Scope: Ice and Fire CE 2.2.1 for Minecraft 26.1.2 / NeoForge 26.1.2.97.

## Cause and behavior

The death worm still used an AI goal to move toward a point calculated from the
rider's view direction. Player-controlled vehicles are simulated by the rider's
client, where that server AI does not supply movement. The worm inherited the
default ridden input and speed methods, so pressing W supplied no useful input
to the local vehicle simulation.

The worm now runs the original target-based riding logic through the ridden
movement callback on the authoritative client. It uses the horizontal position
of a target ten blocks along the rider's look vector, then ticks the ground
move and jump controls.
The move controller supplies both the forward walking input and the speed;
the normal ridden speed method uses that controller-produced speed.

Controls follow the original 1.16.5 / 1.20.1 riding goal:

- W selects a target ahead of the rider's view.
- S selects a target behind that view and applies the 0.15 speed multiplier.
- A/D select targets to the left/right and apply the 0.25 speed multiplier.
- S takes priority over A/D; A/D take priority over W. W+A therefore selects
  the left target, rather than combining forward and sideways motion.
- S+A and S+D apply both reductions, as in the original goal.
- The ground controller turns toward the target, at most 90 degrees per tick,
  and walks forward. It does not directly strafe or walk backward while locked
  to the rider's yaw. With no movement input it retains its movement heading.
- The full look vector is retained. Looking exactly vertically leaves the
  horizontal target within the move controller's stopping tolerance.

The original controller's slow walking behavior is preserved, including the
additional slowdown from using its walking input as well as its speed. The
existing explicit jump control runs in the ridden callback on the authoritative
instance. The previous preview's direct strafing and diagonal controls have
been replaced.

The riding goal continues to reserve movement, looking, and jumping controls and
stop autonomous navigation and target selection. It no longer issues competing
move-controller destinations. The double-fishing-rod mounting requirement and
unmounted movement code are preserved.

## Automated verification

From the project root, with the configured Java toolchains:

```powershell
.\gradlew.bat -Pissue300Regression runClient --console=plain
.\gradlew.bat -PauditRegression runGameTestServer --console=plain
.\gradlew.bat clean build --console=plain
```

The client test creates an isolated flat world under
`build/issue300-client-runtime`, equips both fishing rods on the server, mounts
the worm through its interaction handler, and drives actual LocalPlayer key
mappings. It checks forward, backward, left, right, turning, W+A, W+D, S+A,
S+D, looking straight up/down, idle, jump, sand-surface movement, and dismount.
It verifies movement headings, the turn limit, key priority, speed multipliers,
and the integrated server's vehicle position. It does not call the ridden
callbacks directly to simulate movement.

Check `build/issue300-client-runtime/issue300-client-result.json` for
`passed: 15, failed: 0`; the successful client exits automatically. Copy the
result before `clean`, which removes the test world and logs. The ordinary
release JAR must not include the opt-in regression classes or test structure.

On 2026-11-20, the initial client test reproduced the unchanged implementation:
forward input produced displacement `(0, 0, 0)`. After restoring target-based
steering, all 15 updated client scenarios passed, including the original key
priorities and controller-based movement. At the test worm's default scale,
S+A/S+D turned toward the rear but produced no displacement: the original
combined slowdown leaves the walking input below the movement threshold.
The clean release build passed, and its JAR contains no opt-in regression
classes or test structure. This covers an actual integrated client/server
session; dedicated multiplayer and modpack compatibility have not been tested.

## Manual preview

1. In a separate test instance, summon a worm using
   `/summon iceandfire:deathworm ~ ~ ~ {WormAge:5,Scale:1.0f}`.
2. Hold a fishing rod in each hand and interact to mount. Check W/S/A/D and the
   turn toward each target. W+A/W+D should select the side direction; S+A/S+D
   should select the rear direction with both speed reductions.
3. Turn the camera while stationary: it should not force the movement heading
   to follow the rider. Looking exactly straight up/down while pressing W should
   stop horizontal movement, matching the original target calculation.
4. Cross grass and sand, step onto a one-block obstacle, press Space to jump, and
   release all movement keys to check that the worm stops drifting.
5. Dismount with Shift, then remount. Check that unmounted worms still move
   autonomously and that a second player sees the ridden worm move normally.
